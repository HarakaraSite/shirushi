# Shirushi サーバーサイド確認メモ

> 確認日: 2026-06-13

## 対象ファイル

- `main.go`

## 修正候補

### 1. UNIQUE マイグレーションで bookmark_tags が失われる可能性

対応状況: 対応済み（2026-06-13）

`migrateAddUniqueURL()` は `bookmarks` テーブルを `bookmarks_new` に作り直したあと、旧 `bookmarks` を `DROP TABLE` しています。

影響:

- `bookmark_tags` の外部キーが `bookmarks` を参照しているため、外部キー制約が有効な状態で旧テーブルを削除すると、関連する `bookmark_tags` が CASCADE で削除される可能性があります。
- 既存DBにタグ紐付けがある状態で初回マイグレーションすると、ブックマーク本体は残ってもタグとの紐付けが消えるリスクがあります。

対応案:

- マイグレーション前に `bookmark_tags` を一時テーブルへ退避し、`bookmarks` 再作成後に存在する `bookmark_id` / `tag_id` だけ復元する。
- または、単純な `CREATE UNIQUE INDEX IF NOT EXISTS ... ON bookmarks(url)` で足りるか検討する。

### 2. メタデータ取得のリダイレクト先検査

対応状況: 対応済み（2026-06-13）

`fetchMetadata()` は `Transport.DialContext` で接続先IPを検査しており、SSRF対策が入っています。

確認ポイント:

- Go の HTTP クライアントはリダイレクトを自動追跡します。
- リダイレクト後も同じ `Transport` を通るため接続先IP検査は効く想定ですが、URLスキームやリダイレクト回数の扱いを明示しておくとより安全です。

対応案:

- `CheckRedirect` を設定し、リダイレクト回数を制限する。
- `http` / `https` 以外のスキームを早めに拒否する。
- レスポンスの `Content-Type` が HTML 系でない場合は本文を読まずに中断する。

### 3. URLバリデーションが弱い

対応状況: 対応済み（2026-06-13）

ブックマーク作成・更新・メタデータ取得では、URLが空かどうかは確認していますが、URLとして妥当か、許可するスキームかは十分に検証していません。

影響:

- `javascript:` や `file:` など、ブラウザ側では `safeHref()` で無害化されるURLもDBには保存できます。
- 将来CLIや別クライアントを追加したとき、同じ前提で守られるとは限りません。

対応案:

- サーバー側でも `net/url` でパースし、保存対象は原則 `http` / `https` に限定する。
- 必要ならローカル用途向けに許可スキームを明示する。

### 4. JSON入力サイズの上限がない

対応状況: 対応済み（2026-06-13）

JSON API は `json.NewDecoder(r.Body)` で直接読み込んでおり、リクエストボディサイズの上限がありません。

影響:

- 巨大なJSONを送られた場合、メモリや処理時間を余分に消費する可能性があります。

対応案:

- `http.MaxBytesReader` でAPIごとに入力サイズ上限を設定する。
- 例: ブックマーク作成・更新は数十KB、一括操作は件数上限も合わせて設ける。

### 5. 一括操作の件数上限がない

対応状況: 対応済み（2026-06-13）

一括削除・一括タグ追加・一括タグ削除では、ID配列の長さに上限がありません。

影響:

- 非常に大きな配列を送ると、SQLのプレースホルダーが大量生成され、SQLiteの上限やメモリ使用量に当たる可能性があります。

対応案:

- 一括操作の最大件数を決める。
- 例: 1リクエストあたり1000件まで、など。

### 6. タグ紐付けAPIが存在確認を返さない

対応状況: 一部対応済み（2026-06-13）

`handleAddTagToBookmark()` は `INSERT OR IGNORE` を使っており、存在しない `bookmark_id` や `tag_id` を指定した場合、外部キー制約でエラーになるケースはあります。

確認ポイント:

- 外部キー制約が常に有効なら不正IDはエラーになります。
- ただし、エラー時はすべて `500` になり、クライアントからは入力不正なのかサーバー障害なのか分かりにくいです。

対応案:

- 事前にブックマーク・タグの存在確認を行い、存在しない場合は `404` または `400` を返す。
- 一括操作でも「存在しないIDを無視する」か「エラーにする」か仕様を明示する。

### 7. import処理で一部DBエラーを無視している

対応状況: 対応済み（2026-06-13）

`handleImport()` のタグ作成・タグID取得・紐付けでは `db.Exec` / `Scan` のエラーを確認していない箇所があります。

影響:

- タグ作成や紐付けに失敗しても、インポート成功としてカウントされる可能性があります。
- 障害時の原因が見えにくくなります。

対応案:

- タグ作成、タグID取得、紐付けの各エラーを確認し、失敗時はレスポンスに反映する。
- 可能ならインポート全体をトランザクション化する。

### 8. import の DD 抜粋取得が次のブックマークまでまたぐ可能性

対応状況: 対応済み（2026-06-13）

`handleImport()` は `<A>` タグの直後から `reDD` を検索しています。

影響:

- 対象ブックマークに `<DD>` がなく、次のブックマークに `<DD>` がある場合、次の説明文を誤って拾う可能性があります。

対応案:

- 現在の `<A>` から次の `<DT><A` までの範囲だけを検索対象にする。

### 9. Cookie削除時の属性がログイン時と揃っていない

対応状況: 対応済み（2026-06-13）

ログイン時のCookieには `HttpOnly` と `SameSite=Strict` が付いていますが、ログアウト時の削除Cookieには `HttpOnly` / `SameSite` が付いていません。

影響:

- 多くのブラウザでは `Name` / `Path` が一致すれば削除できますが、属性を揃える方が安全で分かりやすいです。

対応案:

- ログアウト時の削除Cookieにも `HttpOnly: true` と `SameSite: http.SameSiteStrictMode` を付ける。

### 10. HTTPサーバーのタイムアウトが未設定

対応状況: 対応済み（2026-06-13）

`http.ListenAndServe` を直接使っており、ReadTimeout / WriteTimeout / IdleTimeout が設定されていません。

影響:

- 低速なクライアント接続に対してリソースを長く保持する可能性があります。

対応案:

- `http.Server` を明示的に作り、`ReadHeaderTimeout` などを設定する。

## 確認済みの良い点

- SQLは基本的にプレースホルダーを使っており、直接文字列連結している箇所もID数に応じた `?` 生成が中心。
- 認証トークンは `crypto/rand` で生成されている。
- セッションマップは `sync.Mutex` で保護されている。
- Cookieに `HttpOnly` と `SameSite=Strict` が設定されている。
- メタデータ取得にはタイムアウト、1MBの読み込み制限、User-Agent、SSRF対策のIP検査が入っている。
- 一覧取得はタグを一括取得しており、N+1クエリを避けている。
