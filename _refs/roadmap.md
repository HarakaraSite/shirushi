# Shirushi ロードマップ

> 作成日: 2026-06-14

## 方向性

Shirushiは、Shioriに近い軽量ブックマーク管理アプリから出発しつつ、単なるURL保存ではなく、個人の研究・関心記録を育てるためのツールにしていく。

重視する流れ:

```text
検索する
  -> 関心のまとまりを見つける
  -> 複数選択する
  -> タグ付け / タグ削除 / チェック / 要約 / メモ追記
  -> 研究ログとして整理される
```

このため、Shirushiでは「検索からバルク操作へ進む体験」を中核に置く。

## 当面の目標: v1公開

まずは個人Proxmoxサーバ上のForgejoで管理し、必要に応じてCodebergと連携する。
v1では、多機能化よりも、実運用できる安定性・公開時に迷わないドキュメント・基本的な安全性を優先する。

想定公開先:

- 自宅Proxmox上のForgejo
- 外部公開・ミラー候補としてCodeberg

## 直近で実装したい改善

### 1. ページサイズ切り替え

検索からバルク操作に進むには、50件固定では少し窮屈。
ページあたり件数を切り替えられるようにする。

候補:

- 50件
- 100件
- 200件

実装方針:

- APIは `GET /api/bookmarks?page=1&limit=200` を使う。
- サーバー側で許可値または最大値を制限する。
- フロントエンドに件数セレクトを追加する。
- 件数変更時は1ページ目へ戻す。
- `localStorage` に保存して、次回も同じ件数で使えるようにする。

確認したい流れ:

```text
200件表示
  -> 検索
  -> 複数選択
  -> 全て選択
  -> バルクタグ付け
```

### 2. 検索結果とバルク操作のUX改善

- 選択中件数を分かりやすく表示する。
- 「現在ページを全て選択」と「検索結果全体を対象にする」を将来的に分けるか検討する。
- バルク操作後に選択状態をどう扱うか整理する。
- バルクタグ削除後、現在のタグフィルターが空になる場合の表示を確認する。

## 低優先度の既知課題

### サムネイル画像URLが相対パスの場合の404

実DB確認中に `/images/owncast-logo-1000x1000.png` の404を確認した。

想定原因:

- `image_url` に相対パスが保存されている。
- ブラウザがShirushi自身の `/images/...` として取りに行く。

影響:

- サムネイルが欠けるだけで、DB整合性やバルク操作には影響しない。

対応案:

- メタデータ取得時に相対 `og:image` をページURL基準で絶対URLへ変換する。
- 既存DBの相対 `image_url` を調査・補正する。
- 変換できない相対URLは保存しない。
