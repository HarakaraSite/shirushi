# サブエージェント移譲指針

この文書は、親エージェントが調査、設計、実装、reviewをサブエージェントへ委譲するときの判断基準を定める。
最終的な判断、変更の統合、検証、完了責任は親エージェントが持つ。

## 1. 移譲判断

- 局所的で方針が明確な変更は、親エージェントが直接行う。
- 調査範囲が広い、不確実性が高い、専門的判断が必要、または独立した観点を並行確認できる場合は、サブエージェントへの移譲を優先して検討する。
- 広範囲な調査ほど移譲の便益は大きい。ただし、1エージェントへ無制限に丸投げせず、E2E、backend、release契約、文書整合など、独立して調査・判断できる観点へ分割する。
- ファイル数や行数を固定閾値にせず、依存関係、判断の独立性、専門性、統合コストを基準にする。
- 読み取り専用の独立調査は並列実行してよい。複数の変更作業を並列実行する場合は、隔離したworktreeを使う。

## 2. Agentの選択

- 関連箇所と事実の収集には`scout`を使う。
- 段取り、選択肢比較、設計判断には`planner`を使う。
- 外部仕様や一次情報の確認には`researcher`を使う。
- 独立して切り出せる実装には`worker`を使う。
- 実装後の欠陥、回帰、契約違反の確認には`reviewer`を使う。
- 役割を形式的に経由させず、委譲の便益がある場合だけ使う。

## 3. タスク割り当て

委譲時は、少なくとも次を明示する。

1. 目的と最終的に判断したいこと
2. 調査・変更対象と対象外
3. 完了条件
4. ファイル変更の可否
5. 期待する出力形式と優先順位
6. 使用可能なtoolと環境上の制約
7. 親が確認済みで再調査不要な事実

タスクは次の原則で設計する。

### 3.1 Toolをagentへ合わせる

- named agentへ、そのagentで許可されていないtoolを指定しない。
- 許可toolが不明な場合は、tool指定を省略してagentの既定値を使う。
- validation error、tool制約違反、実行時エラー、timeoutを区別して扱う。

### 3.2 責任を詰め込みすぎない

- 1タスクへ事実収集、設計、実装、総合reviewを過剰に詰め込まない。
- 必要に応じて段階または観点ごとに分ける。
- `scout`には事実、`planner`には判断、`worker`には変更、`reviewer`には完成差分の確認を依頼する。
- 広範囲な調査は移譲対象としつつ、複数agentが独立して進められる観点へ分割し、親が結果を統合する。

### 3.3 完了条件を具体化する

- 「具体的に調査する」だけでなく、確認項目と報告すべき判断を列挙する。
- 成功条件、blocking条件、未確認事項の扱いを指定する。
- 変更を許可する場合は、変更可能な範囲と必要な検証を指定する。

### 3.4 出力を制御する

- finding数、推奨案数、代替案数などを必要に応じて制限する。
- blocking、non-blocking、未確認事項など、親が統合しやすい形式を指定する。
- 広い調査であっても、関連性の低い探索や報告を無制限に広げない。

### 3.5 適切な段階で呼ぶ

- 現状把握には`scout`、方針決定には`planner`、実装後の独立確認には`reviewer`を使い分ける。
- `reviewer`には可能な限り完成差分、採用方針、実行済みの検証結果を渡す。
- 未完成状態の広範な推測を`reviewer`へ依頼するより、先に事実収集または実装を進める。

## 4. Timeout

- timeoutは期待完了時間ではなく、異常停止を防ぐための安全上限として設定する。
- 読解、tool実行、thinking、最終報告のすべてがtimeoutへ含まれることを考慮する。
- 親エージェント自身が同じ作業を完了できない時間を、サブエージェントのtimeoutに設定しない。
- deep、high、xhigh thinkingを使うagentへ、120〜180秒の短いtimeoutを設定しない。

目安は次のとおりとし、調査範囲、tool実行回数、thinking levelに応じて延長する。

| タスク | Timeoutの目安 |
|---|---:|
| 局所的な`scout` | 300〜600秒 |
| 複数領域を横断する`scout` / `reviewer` | 600〜900秒 |
| 設計判断を含む`planner` / `reviewer` | 900〜1200秒 |
| repository全体または外部調査を含む作業 | 1200秒以上 |

- highまたはxhigh thinkingでは、目安の長い側を選ぶ。
- 長時間作業は可能ならasyncで開始し、親は独立作業を継続する。`status`や`logs`で進行を確認してから`wait`する。
- timeoutをそのまま調査失敗やagent能力不足と判断しない。進捗とlogを確認し、処理が継続していた場合は、同じ範囲のままtimeoutを延長して再実行する。
- timeout回避だけを目的に、本来必要な調査範囲を狭めない。分割は専門性、独立性、結果統合のしやすさを高めるために行う。

## 5. 統合と検証

- サブエージェントの結論をそのまま採用せず、根拠となるコード、一次資料、実行結果を親が確認する。
- 複数agentの結果が競合した場合は、親が実コード、一次資料、再現可能な検証を基準に判断する。
- サブエージェントが変更した場合も、親がdiff、テスト、文書整合を最終確認する。
- 複数の変更結果を統合する場合は、競合だけでなく、個別には見えなかった組合せ上の回帰も確認する。
- timeoutや部分結果を含め、最終的な完了責任は親エージェントが持つ。
